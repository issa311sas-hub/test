# 第4章 実装

本章では，第 3 章で述べた設計に基づいて構築した評価基盤の実装について述べる．

## 4.1 実行環境とシステム構成

実装は Windows 11 上の Python 3.12 で行い，モデルへの接続には Anthropic
Messages API を用いた．較正指標の計算は scikit-learn などを用いず numpy のみで
実装している．指標の定義を式から直接実装することで，ライブラリの仕様に依存した
解釈の揺れを避けるためである．

実装はモジュールごとにファイルを分けた．構成を表 4.1 に示す．この分割により，
解析の不具合を修正した際に，モデルへの問い合わせをやり直さずに結果を再計算
できる．実際にこの仕組みが必要になった経緯は 4.4 節で述べる．

表 4.1 モジュール構成

| ファイル | 役割 |
|---|---|
| `fetch_mgsm.py` | データセットの取得と実験用形式への変換 |
| `prompts.py` | 引き出し方式ごとのプロンプト生成 |
| `run_pilot.py` | モデルへの問い合わせと結果の記録 |
| `parser.py` | 応答の解析と正誤判定 |
| `calibration.py` | 較正指標と Murphy 分解の計算 |
| `compare_methods.py`，`bootstrap_ci.py` | 方式間の比較・作図と信頼区間の算出 |
| `rescore.py` | 保存済み応答からの再採点 |
| `test_parser.py`，`test_calibration.py` | 単体テスト |

## 4.2 プロンプト生成とモデルへの問い合わせ

`prompts.py` は，引き出し方式と問題形式の組み合わせに応じてテンプレートを
選び，問題文を埋め込む．多肢選択の問題で選択肢が空の場合は，選ぶ対象が提示され
ないままモデルが記号を答えることになるため，明示的に例外を送出する検査を実装した
（4.4 節）．

`run_pilot.py` は問題を 1 問ずつ処理し，問題の識別子，方式，正解，モデルの
回答，確信度，正誤，解析の成否，およびモデルの応答全文を CSV に記録する．
応答全文を保存しているのは，解析の不具合が後から見つかった場合に，API を
呼び直さずに再採点できるようにするためである．ただし Verb.2S については保存が
不完全である．記録される応答全文は第 2 ターンのものであり，第 1 ターンの応答は
抽出後の回答だけが残る．したがって Verb.2S では回答の再抽出ができず，回答の
抽出に関わる不具合を後から修正できない．今後は両ターンの応答全文を別の欄に
保存する．

一時的な通信エラーやレート制限に対しては待ち時間を倍にしながら再試行するが，
型の誤りや設定の不備といった，再試行しても解消しない種類の例外は対象から
除外した．また温度は，サンプリングの指定を受け付けるモデルにのみ送り，どちらとも
判断できないモデル名が指定された場合は警告を表示する．温度を指定しなければ
出力に揺らぎが生じ，予備実験が前提としている条件から外れるためである．

## 4.3 応答の解析と正誤判定

`parser.py` は，モデルの応答から回答と確信度を抽出する．モデルが指定された
形式から外れた応答を返すことがあるため，複数の正規表現を順に試す実装とした．
また，モデルが仮の記入をしてから途中式を書き，最後に本来の答えを書く場合が
あるため，回答は応答中で最後に現れたものを採る．このとき，見出しの種類
（「回答:」「Answer:」など）の優先順ではなく，応答中の出現位置で判断する．

確信度の解析は方式によって異なる．Verb.1S と Verb.2S では数値を抽出する．
プロンプトでは 0.0 から 1.0 の範囲を指示しているが，モデルが 0 から 100 の
尺度で答える場合があるため，値が 1.0 を超えるときは 100 で除して正規化する．
百分率記号が付いている場合は，値域によらず 100 で除す．値域だけで尺度を判断
すると，「確信度: 0.5%」を 0.5，すなわち 50% と読み違えるためである．
Ling.1S では表 3.1 の言語表現を抽出し，対応する数値に変換する．このとき，
短い表現が長い表現の一部に一致して取り違えが起きないよう，文字数の多い表現
から順に照合する．

正誤判定は回答形式に応じて切り替える．数値の場合は，正解と回答の双方に同一の
正規化を施し，正規化後の文字列全体が単一の数値として読める場合にかぎり数値と
して比較する．許容する表記は，全角の数字と記号，囲みの括弧 1 組（`[32]` など），
末尾の百分率記号 1 つ，および 3 桁区切りとして正しいカンマに限り，分数
（`1/2`），指数表記（`1e3`），複数の値を含む回答（`32 or 64`）はいずれも
誤答として扱う．文字列の一部に数字があれば採用する方式では `1/2` を `1` と
して受理してしまい，表記の正規化を超えて意味の異なる回答まで正答としてしまう
ためである．なお，単位の語（`円`，`個`，`cm` など）は取り除かない．正解欄に
単位が無いことは，回答側の単位を消してよい理由にはならないためである．予備
実験のデータでは単位を伴う回答は現れなかったため，この制約は結果に影響しない．

`calibration.py` は 3.4 節の定義をそのまま実装している．`bootstrap_ci.py` は，
問題を復元抽出して指標を計算し直す操作を繰り返し，得られた分布の 2.5 パーセン
タイルと 97.5 パーセンタイルを区間の端とする．ここで重要なのは，3 方式が
まったく同じ問題集合に対して実行されている点である．したがって再抽出は方式
ごとに独立に行わず，問題ごとに 3 方式の結果を組にして同じ添字で抽出する．
独立に抽出すると問題単位の対応関係が失われ，差の分散が方式間の共分散を反映
しなくなる．

## 4.4 実装過程で判明した不具合

予備実験の実施にあたり，結果を無効にする不具合が 6 件見つかった．いずれも
実行時にエラーを発生させず，出力された数値が一見正常に見えるものであった．

実験の実施前に見つかった 4 件は，選択肢を持たない問題への多肢選択テンプレート
の適用，確信度の見出し語の不一致（プロンプトは「確信度」を求めているのに解析
側は「信頼度」「自信度」のみを照合していた），尺度の二重変換（0.9 を 0.009 と
して扱っていた），および Ling.1S における確信度の欠損（方式によらず数値用の
解析を適用していた）である．いずれも該当する処理を修正し，1 件目については
自作した予備データの使用を取りやめて MGSM に変更した．

外部のレビューを受けて実施後に見つかった 2 件は，結果への影響が大きい．
1 件目は，数値の比較において回答側だけカンマを除去し，正解側はそのまま数値へ
変換していたものである．正解が `2,125` の形式であると変換に失敗して部分一致の
判定に移るため，正しい回答が誤答として記録されていた（3 方式で 4 件）．
2 件目は，応答中で最初に現れた回答を採っていたものである．モデルが仮の記入を
してから途中式を書き，最後に本来の答えを書く場合，仮の記入のほうが回答として
記録されていた．確認できた範囲で Verb.1S に 2 件，Ling.1S に 13 件発生しており，
方式によって発生数が偏っていたため，修正前の正答率の差には採点処理の影響が
混入していた．なお Verb.2S は第 1 ターンの応答を保存していないため，同種の
不具合が何件あったかを確認できない．

この 2 件は `rescore.py` により保存済みの応答から再採点した．再採点の前後で
正答数は Verb.1S が 211 から 215，Verb.2S が 218 から 221，Ling.1S が 181 から
195 に変化した．第 5 章に示すのはすべて修正後の値であり，同種の誤りを検出する
ための回帰テストを `test_parser.py` に追加した．

6 件はいずれも，エラーを出さずに誤った数値を出力する種類の不具合である．指標が
計算できたことをもって処理が正しいと判断してはならず，モデルの応答全文と解析
結果を目視で確認する工程が必要である．
